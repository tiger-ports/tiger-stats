# Stats Tiger — initial foundation

A small, independent Objective-C/C rewrite inspired by [exelban/Stats](https://github.com/exelban/Stats), **not a complete port**. This foundation has a status-item menu, live aggregate CPU utilization, an approximate physical-memory display, root-filesystem disk capacity, local network-interface throughput, and a disk-space explorer with an explicitly confirmed single-file Move to Trash action. It contains no upstream source code or assets; upstream Stats is MIT licensed. No network connections, login item, telemetry, privileged operations, or external dependencies are implemented.

## Build and test locally

Requires Apple's command-line developer tools and Cocoa. From this directory:

```sh
make clean
make test
build/Stats-Tiger.app/Contents/MacOS/Stats-Tiger --self-check
```

The `--self-check` takes two Mach CPU and network-interface samples one second apart, prints live deltas, a memory sample and root disk capacity, exits nonzero on sampling/format errors (including no eligible network interfaces or a changing interface set), and does not initialize or launch the GUI. `make test` also runs deterministic C tests and a headless CLI integration test. The app bundle is `build/Stats-Tiger.app`; it is not installed or automatically launched. To enforce warnings as errors locally, use `make clean && make test CFLAGS='-O2 -Wall -Wextra -Werror -Wno-deprecated-declarations -std=gnu99'`.

The supplied local artifact was built on macOS 15.8.2 x86_64 using the modern SDK and targets macOS 15.0. **It cannot be used as a Tiger/PowerPC binary.** The current compiler does not provide a working PowerPC Darwin 8 target. Nothing has been cross-compiled for PowerPC or run on Tiger.

## Tiger target validation plan (not yet executed)

On an actual PowerPC Mac running Mac OS X 10.4.11, with Apple's Xcode / GCC and the 10.4 SDK installed, copy the **source** to a separate directory and build locally:

```sh
make clean
make CC=gcc test
build/Stats-Tiger.app/Contents/MacOS/Stats-Tiger --self-check
file build/Stats-Tiger.app/Contents/MacOS/Stats-Tiger
```

Confirm the binary architecture is PowerPC, all tests and the self-check pass, and the values are plausible compared with Activity Monitor, `df` for `/`, and successive `/usr/sbin/netstat -ib` interface counters. Exercise interface up/down and counter changes. Only with the owner's permission, launch the built app and verify the status item, CPU updates, memory, disk and network labels, menu and Quit. Watch for toolchain/SDK compile errors, unavailable APIs, crashes, event-loop issues, and incorrect values. Do not copy the macOS 15 build to Tiger as a substitute for rebuilding. The declared 10.4 minimum in the plist is an intended deployment target, not proof of compatibility.

Code deliberately uses manual retain/release, no blocks or Swift, legacy `NSStatusItem` APIs and `HOST_CPU_LOAD_INFO`/`HOST_VM_INFO`. The status-item and Mach constants were checked against a 10.4u SDK, but the complete source has **not** been built or tested against it. Availability of every other API and behavior still requires target validation.

## Measurement semantics and limitations

### Disk explorer and Move to Trash

Choose **Explore Disk Space...** in the status menu and explicitly choose a directory. Scanning starts only then, on a background thread. The window shows a size-sorted list and a coloured donut for immediate children; matching list colours identify slices. Sizes display in readable binary units (B, KiB, MiB, GiB, TiB, PiB, EiB) with at most one decimal place, rounded half-up. Select a directory and click **Open selected folder** (or double-click it), and use **Up** to return. The list includes zero-byte entries and excluded symlinks. The first 64 entries have coloured slices; later entries are combined in grey. There is no elevation or command that opens files.

Select one regular file and choose **Move to Trash**; the confirmation shows its full absolute path. Nothing is moved automatically. Directories, symlinks, special files, foreign-volume items, missing or changed scan identities, unsafe path components, and names that cannot be represented and round-tripped exactly are rejected. Hard-linked files are eligible individually: moving one name does not remove other links. Trash retains files until emptied; the displayed logical size is not a prediction of space immediately freed or reclaimable. No permanent-delete fallback or shell command is used.

Scan launches and Trash submissions are serialized, but an asynchronously accepted Trash operation may still be in progress during later read-only scans. The app checks the identities and types of the selected file and every path ancestor again after confirmation, then calls the native path-based `NSWorkspaceRecycleOperation`. A successful synchronous result invalidates the old tree and starts a fresh scan. A positive operation tag means completion is **unverified**; further Trash operations remain disabled for the lifetime of this explorer, including after closing and reopening its window. A contradictory failure with a positive tag is also treated as pending. Read-only refresh continues and the chart is explicitly provisional because the operation may still change the filesystem during a scan. Neither a notification nor a file's disappearance confirms completion; the app never automatically retries the operation. Quitting the app does not prove a pending operation completed.

**Safety limitation:** identity checks and the native operation are separate path-based calls; an adversarial filesystem can replace a path between validation and the Workspace call. Inode reuse can also defeat identity checks. This is not an atomic binding or a security guarantee. A root whose absolute path contains symlinks, noncanonical components, or unrepresentable bytes cannot be used for Trash even if it can be scanned. User permissions, Finder/Workspace behavior, and the availability of Trash on a particular volume can cause failure.

While the explorer remains open, it attempts a background rescan every 30 seconds; **Refresh** starts one manually, including while a Trash outcome is unverified. This is polling, not immediate change notification: results arrive only after a scan finishes, and a long scan or modal dialog can delay or skip an attempt. Scans never overlap and a file cannot be moved while scanning. The previous tree stays visible during ordinary refresh; a successful refresh resets navigation to the selected root, while a failed ordinary refresh reports the error and retains the previous tree. That error remains visible while a retry is in flight and clears when a new scan succeeds. After an attempted Trash operation, stale results are discarded even on failure. Partial results are flagged. The existing per-scan limits still apply.

Sizes are logical `st_size` bytes, **not allocated blocks, reclaimable space, or Finder storage**. The readable binary units (B, KiB, MiB, GiB, TiB, PiB, EiB) shown in the list and status line are a formatting of those same logical counts — at most one decimal place, rounded half-up, with a round-up carrying into the next unit (for example, 1023.99 KiB shows as 1 MiB) — and the UI states that the values are logical bytes, not allocated or reclaimable space. The unit formatting never changes what was measured. Each hard-linked regular file is counted only once for the entire scan, assigned to the first path visited in name-sorted depth-first order; later links show zero even if they are in another folder. Under the node cap the included directory entries depend on filesystem enumeration order. Symlinks and special files contribute zero and symlinks are never intentionally traversed. Each scan is limited to 10,000 nodes, depth 64, and the selected filesystem. Read failures, limits, overflow, and filesystem boundaries produce visibly incomplete results. A root scan failure displays an error; per-item read failures are marked unreadable. Files may change during scanning, so totals are not a snapshot.

Closing the window stops the refresh timer but does **not** cancel a scan already in flight. Its result is discarded, even if the window is reopened before it completes. Reopening during that scan returns to the same selected folder and waits for the old scan to finish before starting a fresh one; no scan is started while closed. At process exit an outstanding worker may be terminated by the OS. A slow or blocked filesystem can delay completion despite the node and depth limits. Directory entries are checked against opened-directory identity and symlinks are not intentionally followed, but path-based ancestor replacement remains a TOCTOU limitation: this is **not a security sandbox** against a filesystem changing adversarially. Navigation itself only uses the already scanned tree.

* CPU busy = deltas of user + system + nice ticks divided by all four deltas, including idle. Deltas use unsigned 32-bit modular arithmetic, accounting for at most one wrap per counter per interval. Counter resets or multiple wraps between samples cannot be distinguished from legitimate wrap. Zero total deltas are reported as unavailable. The UI samples approximately every second.
* Physical total comes from the 64-bit `hw.memsize` value; if that cannot be read, memory is shown as unavailable rather than risking a truncated 32-bit fallback. Available is approximated as Mach free + inactive pages; used is physical total minus that estimate. Available is capped at total. This is **not** modern memory pressure or necessarily equal to Activity Monitor, particularly on newer macOS with compression and differing VM accounting.
* `Root disk available: X / Y GiB` uses `statfs("/")`: X is `f_bavail` blocks available to non-superusers and Y is total `f_blocks`, both multiplied by `f_bsize` and divided by 2^30. This is capacity, **not disk activity**, and available is not the same as all free space (`f_bfree`). Values are rounded to one decimal. The menu shows unavailable if sampling fails or reports invalid/overflowing values; the self-check instead exits nonzero. On modern macOS, `/` may be a system volume sharing APFS container space, not the writable data volume or a whole physical disk; quotas, snapshots, reservations, and purgeable space can make this differ from Finder or space actually writable. Older filesystems/ABIs may have their own reporting limits; Tiger behavior is unverified.
* Network: `getifaddrs` supplies `AF_LINK` interface byte counters; only interfaces marked both up and running and not loopback are included. Each selected entry is keyed by name and link index; duplicate/invalid entries, missing statistics, no eligible interfaces, and more than 128 interfaces are unavailable. Rates are the sum of per-interface byte deltas in KiB/s. A changed interface set or a decrease in either counter invalidates the entire interval and establishes a new baseline; read errors clear the baseline. A nonpositive or over-10-second interval is unavailable and rebaselined; invalid timestamps clear it. No counter width or wrap is assumed. The real Tiger SDK declares `getifaddrs`/`freeifaddrs` and `ifa_data`, and Tiger's libSystem exports the functions; the complete implementation and its counter semantics still require a Tiger build and runtime validation. Apple documents `AF_LINK` data as `struct if_data` ([manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/getifaddrs.3.html)).
* Network limitations: a counter reset or complete wrap that ends at a value at least as large as before cannot be detected, nor can a removal and re-addition with the same name and index between samples. Counters may have platform-specific width and semantics. Virtual/tunnel interfaces may count the same traffic as physical interfaces, so the sum is not necessarily Internet traffic. The timestamp uses wall-clock `gettimeofday`, not a monotonic clock: backward jumps and overly long intervals are rejected, but smaller adjustments that still produce a valid positive interval are undetectable and can distort rates. Snapshot collection takes time and interfaces need not be sampled simultaneously; up/running flags are not a guarantee of actual link activity.
* No per-core views, settings, sensors, fans, disk activity, battery, Bluetooth, process details, widgets, persistence, localization, launch-at-login, updater, or other upstream modules yet. A synthetic chart was rendered offscreen and inspected on the base Mac; the complete explorer GUI has not been launched or visually exercised on either system.
